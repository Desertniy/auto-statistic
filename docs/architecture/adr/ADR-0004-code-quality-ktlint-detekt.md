# ADR-0004: Качество кода — ktlint (стиль/форматирование) + detekt (статический анализ), ронят `build`
- Статус: Accepted
- Дата: 2026-10-23
- Фича: F-001

## Контекст
Пользователь требует проверки качества сразу и с падением сборки (Q3 в F-001). Нужны две разные вещи:
1) единый стиль с автоформатированием; 2) статический анализ (сложность, «магические числа», запахи кода).
Ограничение: стабильная линия detekt 1.23.x поддерживает Kotlin только до 2.0.x и Gradle до 8.12, а проект на
Kotlin 2.3.21 / Gradle 9.3.1 (ADR-0002). Линия detekt 2.0 на 2026-10-23 существует только в alpha
(последняя — 2.0.0-alpha.6), при этом в таблице совместимости detekt:
`2.0.0-alpha.3 — Gradle 9.3.1, Kotlin 2.3.21`, т.е. ровно наш стек.

## Решение
1. **ktlint** через Gradle-плагин `org.jlleitschuh.gradle.ktlint` **14.2.0**, движок ktlint **1.8.0** (версия
   задаётся явно в `ktlint { version = ... }`).
   - Стиль — `ktlint_official` через `.editorconfig` в корне (единый источник правил и для IDE).
   - Проверяются main, test и `*.gradle.kts`. Задачи `ktlintCheck` (входит в `check`) и `ktlintFormat` (автоисправление).
   - *Дополнено 2026-10-24 (ревью кода T03):* **неиспользуемые импорты контролирует ktlint** — в секции `[*.{kt,kts}]`
     `.editorconfig` явно включается `ktlint_standard_no-unused-imports = enabled`. В ktlint 1.8.0 правило помечено
     `@Deprecated` («Marked for removal in Ktlint 2.0.0») и без явного включения не запускается. Включаем его осознанно:
     оно работает в `ktlintCheck` (вывод `файл:строка:колонка Unused import (standard:no-unused-imports)`), а `ktlintFormat`
     удаляет такой импорт. Ограничение: правило без type resolution, работает эвристически (по имени в файле). **Пересмотреть
     при переходе на ktlint 2.0**, когда правило удалят: тогда выбрать замену, например detekt `UnusedImport` с type resolution
     (см. «Рассмотренные альтернативы»).
2. **detekt 2.0.0-alpha.3** через плагин `dev.detekt` (версия фиксирована в каталоге, `toolVersion` совпадает).
   - `buildUponDefaultConfig = true`, `allRules = false`, конфигурация-дельта `config/detekt/detekt.yml`
     (только переопределения дефолтов), `ignoreFailures = false`, `failOnSeverity = FailOnSeverity.Error`
     (`dev.detekt.gradle.extensions.FailOnSeverity`) — задаётся явно, чтобы порог падения не зависел от дефолтов alpha.
   - Версия 2.0.0-alpha.3 подтверждена пользователем (2026-10-23) как допустимая.
   - В `check` входит задача `detekt` (без type resolution, источники `src/main/kotlin` и `src/test/kotlin`).
     Задачи с type resolution (`detektMain`/`detektTest`) в `check` не подключаются — можно включить отдельным решением.
   - Правила форматирования detekt (`detekt-rules-ktlint-wrapper`) **не подключаются**: форматированием владеет
     ktlint. Правила detekt, дублирующие ktlint (`MaxLineLength`), отключаются в `detekt.yml`, чтобы не было
     двух источников истины.
   - Baseline не используется: кодовая база пустая, нарушений быть не должно.
   - *Дополнено 2026-10-23 ([ADR-0005](./ADR-0005-kotest-testing.md)):* в `detekt.yml` включается `style>ForbiddenImport`
     с запретом `org.junit.*`, `org.assertj.*`, `org.hamcrest.*`, `kotlin.test.*` — автоматический контроль правила
     «тесты только на Kotest». Тесты — спецификации `FunSpec` со строковыми именами (не backtick-функции), поэтому правила
     именования функций (`FunctionNaming` detekt, `function-naming` ktlint) на тестовый код не влияют.
3. Обе проверки — часть `./gradlew check` → `./gradlew build`; любое нарушение роняет сборку с указанием файла,
   строки и правила. Отчёты: `build/reports/ktlint/`, `build/reports/detekt/`.
4. Команды для разработчика документируются в `docs/architecture/conventions.md` (раздел «Сборка и проверки»).

## Последствия
- Плюсы: автоматический единый стандарт, на который опираются ревью и QA; автоформатирование (`ktlintFormat`)
  снимает стилевые споры; detekt ловит сложность/магические числа/запахи.
- Минусы и риски:
  - **detekt — alpha-версия**: возможны ложные срабатывания и breaking changes конфигурации при обновлении.
    Смягчение: версия жёстко зафиксирована, конфигурация минимальна (дельта), обновление — осознанным шагом.
    Как только выйдет стабильный detekt 2.0.x, совместимый с нашими Kotlin/Gradle, — обновиться (пересмотр ADR не нужен,
    если решение по сути не меняется).
  - Связка версий: detekt привязан к Kotlin/Gradle (таблица совместимости). Обновление Kotlin или Gradle требует
    сверки с таблицей detekt.
  - Если detekt 2.0.0-alpha.3 окажется неработоспособным с нашей сборкой: сначала фиксируется конкретная ошибка
    (в «Реализации» задачи); переход на более новую 2.0.0-alpha.N допустим **только** если она проверенно работает
    на нашем стеке (Gradle 9.3.1 + Kotlin 2.3.21, JDK 17) — зелёный полный `./gradlew build`, включая `detekt`
    и негативную проверку; иначе — эскалация к architect. Более новые alpha в таблице совместимости собраны под
    другой стек (alpha.6 — Gradle 9.6.1 / Kotlin 2.4.10), поэтому их совместимость с нашим не гарантирована.
    Отключение detekt, `ignoreFailures`, baseline или понижение Kotlin/Gradle как обход — не допускаются.
  - Дефолты `MagicNumber` в detekt 2.0 изменились относительно 1.23 (`ignorePropertyDeclaration`,
    `ignoreLocalVariableDeclaration` = true): числа в инициализаторах свойств/переменных не ловятся, только в выражениях
    и аргументах. Принимаем дефолт; учитывать при проверке и ревью.
  - Контроль неиспользуемых импортов держится на deprecated-правиле ktlint `no-unused-imports`. При обновлении ktlint
    до 2.0 правило исчезнет. Ключ в `.editorconfig` при этом, скорее всего, сборку не уронит, и контроль может пропасть молча.
    Смягчение: обновление ktlint — осознанный шаг (версия зафиксирована в каталоге); в чек-лист обновления входит
    негативная проверка «неиспользуемый импорт → `build` падает» и выбор замены (см. альтернативы).
  - Правила detekt, которым нужен type resolution (`@RequiresAnalysisApi`, например `UnusedImport`), в задаче `detekt`
    молча пропускаются: их включение в `detekt.yml` контроля не даёт, пока `detektMain`/`detektTest` не входят в `check`.

## Рассмотренные альтернативы
- **detekt 1.23.8 (stable):** отклонено — официально Kotlin ≤ 2.0, Gradle ≤ 8.12; на Kotlin 2.3 / Gradle 9 работоспособность
  не гарантирована, а «стабильность» без совместимости ничего не даёт.
- **Только ktlint:** отклонено — не покрывает статический анализ (AC-3 T03: сложность, магические числа).
- **detekt с ktlint-wrapper вместо отдельного ktlint:** отклонено — автоисправление через `detekt --auto-correct`
  менее удобно и прозрачно, чем `ktlintFormat`; разделение ответственности инструментов проще для понимания.
- **Spotless (+ktlint):** отклонено — лишний слой абстракции при единственном языке; ktlint-gradle даёт те же задачи.
- **Неиспользуемые импорты через detekt `style>UnusedImport` (2026-10-24):** отклонено для F-001. В detekt 2.0.0-alpha.3
  правило требует type resolution (`@RequiresAnalysisApi`) и работает только в `detektMain`/`detektTest`. Чтобы оно
  заработало, эти задачи придётся добавить в `check`, а это type resolution в каждой сборке, срабатывание `SpreadOperator`
  на `runApplication(*args)` (нужен `@Suppress`) и возможные новые находки alpha. Это дороже одной строки в `.editorconfig`.
  Вернуться к варианту при переходе на ktlint 2.0 или при отдельном решении включить type resolution в `check`.
- **Не контролировать неиспользуемые импорты автоматически (IDE «Optimize Imports» + ревью):** отклонено. Ручной контроль
  противоречит цели ADR (единый автоматический стандарт), а AC-2 T03 называет неиспользуемый импорт примером нарушения стиля.
- **Kotlin `allWarningsAsErrors`:** не включаем в F-001 — предупреждения компилятора от сторонних API могут ломать
  сборку без пользы; решение можно пересмотреть позже.
