# ADR-0012: Журнал аудита безопасности — таблица PostgreSQL, запись вне бизнес-транзакции (fail-open), хранение 1 год
- Статус: Accepted
- Дата: 2026-11-08
- Фича: F-002 (события добавляют F-003 и далее)

## Контекст
PRD QA5, NFR-SEC-3, FR-PD-7: журнал событий безопасности (регистрация, подтверждение email, входы, выходы, позже —
блокировки, смена/восстановление пароля, отказ в доступе к чужому объекту). В записи — время, пользователь (если
известен), IP, User-Agent, тип события, результат; без паролей, токенов и ссылок. Журнал только дописывается,
хранится 1 год в РФ. API просмотра в MVP нет. F-002/T07 AC-6 оставляет архитектору решение, блокировать ли
операцию при сбое записи аудита.

## Решение
1. **Хранение — таблица `security_audit_event` в той же БД PostgreSQL** (размещение в РФ — как у основной БД).
   Колонки: `id uuid`, `occurred_at timestamptz`, `event_type varchar(64)`, `outcome varchar(64)`, `user_id uuid NULL`
   (без FK — запись переживает будущие удаления аккаунтов), `subject_email varchar(254) NULL` (введённый email, когда
   пользователь не определён), `ip inet NULL`, `user_agent varchar(512) NULL`. Индекс по `occurred_at` (очистка).
   Триггер `BEFORE UPDATE` запрещает изменение строк; `DELETE` разрешён только для очистки по сроку.
2. **Модель событий** — `com.autostatistic.audit.domain`: `SecurityEventType` и `SecurityEventOutcome` (enum, значения
   хранятся строками), `SecurityAuditEvent` с фабриками на допустимые сочетания «тип → исход». Новые события следующих
   фич — новые значения enum, без миграции (колонки `varchar`).
3. **Запись** — порт `com.autostatistic.audit.application.SecurityAuditLog.record(event)`; вызывается use case **после**
   завершения бизнес-транзакции (в том числе для неуспешных исходов, где бизнес-транзакции нет), каждая запись —
   отдельный автокоммит `INSERT`.
4. **Сбой записи — fail-open:** `record` никогда не бросает исключение; ошибка пишется в технический лог
   (ERROR `Security audit write failed: type=…, outcome=…, error=<класс исключения>`), пользовательская операция
   завершается своим обычным ответом. Обоснование: аудит не должен блокировать вход/выход при сбое (иначе сбой
   журнала = отказ в обслуживании всех пользователей); доказательство согласия хранится в бизнес-таблице
   `user_consent` транзакционно, а не в журнале.
5. **Хранение 1 год** — `app.audit.retention: P365D`; задача `@Scheduled` (cron `app.audit.purge-cron`, по умолчанию
   ежедневно 03:30 по `Europe/Moscow`) удаляет строки `occurred_at < now − retention`. Запуск на нескольких экземплярах
   безопасен (идемпотентный `DELETE`). Логика — метод `purgeExpired(now: Instant)` application-сервиса, тестируется
   с управляемым `Clock`, без ожидания расписания.
6. **Секреты в журнал не попадают по построению:** у `SecurityAuditEvent` нет полей для пароля, токена или ссылки.

## Последствия
- (+) Простой, транзакционно независимый журнал; запросы оператора — SQL по индексам.
- (+) Сбой журнала не превращается в отказ сервиса.
- (−) При сбое БД аудита событие теряется (остаётся строка ERROR в техническом логе) — допустимо для MVP.
- (−) Неизменяемость защищена триггером и отсутствием API, но не правами БД: владелец схемы может удалить/изменить
  строки. Отдельная роль БД с правом только `INSERT` — при подготовке к запуску (F-011).

## Рассмотренные альтернативы
- **Запись в бизнес-транзакции (fail-closed)** — гарантирует аудит успешных операций, но неуспешный вход не имеет
  транзакции, а сбой журнала блокирует все операции.
- **Только структурированный лог (stdout → сбор логов)** — нет гарантий неизменяемости и хранения 1 год без
  инфраструктуры сбора логов, которой пока нет.
- **Отдельное хранилище/сервис аудита** — избыточно для MVP.
- **Обезличивание вместо удаления по сроку** — сложнее (что считать ПДн в каждой колонке); удаление проще и
  удовлетворяет FR-PD-7.
