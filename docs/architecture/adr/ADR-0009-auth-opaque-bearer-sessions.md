# ADR-0009: Аутентификация — Spring Security, серверные сессии в PostgreSQL, непрозрачный bearer-токен
- Статус: Accepted
- Дата: 2026-11-08
- Фича: F-002 (развивается в F-003)

## Контекст
PRD QA1: выбрать механизм сессий. Требования:
- вход открывает новую сессию, их может быть несколько (FR-AUTH-7); выход **сразу** делает учётные данные
  недействительными (FR-AUTH-8); в F-003 — выход со всех устройств (FR-AUTH-9), сроки 30 дней неактивности /
  90 дней максимум (FR-SES-1), краткоживущие учётные данные с продлением (FR-SES-2, пожелание);
- несколько экземпляров приложения, состояние сессий не только в памяти (NFR-6);
- учётные данные не в URL и не в логах; при cookie — `Secure`/`HttpOnly`/`SameSite` и защита от CSRF (NFR-SEC-2);
- веб-интерфейс — **отдельный проект на своём домене** (PRD Q2, NFR-SEC-5), домен ещё не известен (PRD O1):
  возможно, API и веб окажутся на разных регистрируемых доменах, где cookie становятся сторонними и блокируются
  браузерами;
- все ресурсы, кроме явно публичных, требуют входа (FR-SES-3).

## Решение
1. **Spring Security 7** (`spring-boot-starter-security`, BOM Boot 4.1.2 → Spring Security 7.1.2) — цепочка фильтров,
   правило «по умолчанию закрыто», стандартные заголовки безопасности. Конфигурация — один `SecurityFilterChain`
   в `com.autostatistic.account.infrastructure.security.SecurityConfiguration`:
   - `csrf` выключен (учётные данные не в cookie — CSRF-атака невозможна), `httpBasic`, `formLogin`, `logout`,
     `requestCache` выключены, `sessionManagement` — `STATELESS` (HTTP-сессия сервлета не создаётся);
   - `permitAll` (любой метод) — только явный список публичных путей (architecture.md F-002, раздел «API»), а также
     `DispatcherType.ERROR`; `anyRequest().authenticated()`;
   - `AuthenticationEntryPoint` → 401 ProblemDetail `code = unauthenticated` (формат ADR-0008) и
     `WWW-Authenticate: Bearer`.
2. **Сессия — строка в PostgreSQL** (`auth_session`): `id`, `user_id`, `token_hash`, `created_at`, `revoked_at`.
   Это источник правды для всех экземпляров.
3. **Учётные данные — непрозрачный токен** (не JWT): 32 байта из `SecureRandom`, base64url без паддинга (43 символа).
   Клиент получает его в теле ответа на вход и передаёт в заголовке `Authorization: Bearer <token>`.
   В БД хранится только `SHA-256(token)` в hex (`varchar(64)`, уникальный индекс). Медленный хеш не нужен: у токена 256 бит энтропии.
4. **Проверка на каждом запросе** — свой `OncePerRequestFilter` (`BearerSessionAuthenticationFilter`):
   нет заголовка → запрос идёт анонимно; заголовок есть → поиск активной сессии по хешу (один запрос по уникальному
   индексу); найдена → в `SecurityContext` кладётся `AuthenticatedUser(userId, sessionId)`; не найдена/отозвана/битый
   заголовок → запрос идёт анонимно (публичные эндпоинты работают даже со «старым» токеном, защищённые дают 401).
   Значение токена не логируется ни при каком исходе.
5. **Выход** — `revoked_at = now` для текущей сессии; следующий запрос с этим токеном не находит активную сессию —
   отзыв мгновенный и общий для всех экземпляров. Другие сессии пользователя не затрагиваются.
6. **Развитие в F-003 (целевая модель, чтобы F-003 не перепроектировала механизм):** та же строка `auth_session`
   получает `last_activity_at`, `expires_at` (90 дней), а учётные данные разделяются на краткоживущий access-токен
   (минуты) и одноразовый ротируемый refresh-токен — оба непрозрачные, хранятся хешами в сессии/связанной таблице.
   Выход со всех устройств — `UPDATE auth_session SET revoked_at … WHERE user_id = ?` (понадобится индекс по `user_id`).
   В F-002 выдаётся один токен сессии без срока жизни — сроки вводит F-003/T01 новой миграцией.
7. **Хранение токена на клиенте** — ответственность веб-интерфейса (рекомендация: в памяти, не в `localStorage`);
   риск кражи токена через XSS снижается в F-003 короткоживущим access-токеном.

## Последствия
- (+) Работает при любом размещении веб-интерфейса (разные домены, мобильный клиент) — нет зависимости от cookie.
- (+) Нет CSRF-поверхности; мгновенный отзыв и общий доступ из всех экземпляров — без Redis.
- (+) Простая модель, легко тестируется по HTTP; F-003 расширяет, а не заменяет.
- (−) Один запрос к БД на каждый аутентифицированный запрос (индекс по уникальному хешу; при ~10 000 пользователей
  несущественно; при росте — кеш с коротким TTL или access-JWT, отдельным ADR).
- (−) Токен доступен JavaScript веб-интерфейса (в отличие от `HttpOnly`-cookie) — XSS на фронте опаснее; компенсируется
  F-003 (короткий срок) и F-011 (заголовки, CSP на стороне веба).
- (−) Существующие тесты F-001, ожидающие 404/405 без аутентификации на произвольных путях, меняются: неизвестный путь
  без входа теперь 401 (не раскрывает, какие пути существуют).

## Рассмотренные альтернативы
- **Spring Session JDBC + cookie `SESSION`** — готовые сессии в БД и индекс по пользователю, но cookie требуют
  `SameSite=None` и CSRF-токенов при веб-интерфейсе на другом домене, а сторонние cookie блокируются браузерами;
  домен неизвестен (O1) — риск неработоспособности. Пересмотреть, если API и веб окажутся на одном сайте.
- **JWT (access) + refresh в БД** — без запроса к БД на каждый запрос, но мгновенный отзыв при выходе (FR-AUTH-8)
  требует denylist в БД — та же нагрузка плюс ключи подписи, ротация, риск ошибок валидации JWT.
- **OAuth2 Authorization Server / Keycloak** — избыточно для одного first-party клиента, отдельная инфраструктура.
- **Generic `AuthenticationFilter` / `BearerTokenAuthenticationFilter` (oauth2-resource-server)** — отклоняют запрос
  с невалидным токеном даже на публичных путях и тянут OAuth2-модули; собственный фильтр короче и прозрачнее.
