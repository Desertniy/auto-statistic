# Регламент работы команды агентов

Этот документ — **единый источник правды** о процессе. Каждый агент обязан прочитать его
перед началом работы. Если инструкция агента противоречит этому документу — прав этот документ.

---

## 1. Роли

| Агент (subagent)            | Роль                    | Вход                                  | Выход (артефакт)                                        |
|-----------------------------|-------------------------|---------------------------------------|---------------------------------------------------------|
| `product-manager`           | Продукт-менеджер        | Запрос фичи от пользователя           | `feature.md` + файлы задач `T*.md` в статусе `DRAFT`    |
| `architect`                 | Архитектор              | `feature.md`, задачи в `DRAFT`        | `architecture.md`, ADR, задачи в статусе `PLAN_REVIEW`  |
| `tech-lead`                 | Тимлид                  | План (ревью плана) / код (ревью кода) | Секция «Ревью» в задаче, статус `READY` / `IN_TESTING` / `CHANGES_REQUESTED` |
| `kotlin-backend-developer`  | Kotlin backend-разработчик | Задача в `READY` / `CHANGES_REQUESTED` | Код + тесты, секция «Реализация», статус `IN_REVIEW` |
| `qa-engineer`               | Тестировщик             | Задача в `IN_TESTING`                 | Тест-кейсы, автотесты, секция «Тестирование», статус `DONE` / `CHANGES_REQUESTED` |

Субагенты **не вызывают друг друга напрямую**. Оркестратором выступает основная сессия
Claude Code (см. раздел 6) — она запускает агентов по очереди, ориентируясь на статусы в файлах.
Поэтому **всё общение между агентами идёт через файлы**: что не записано в артефакт — того не было.

## 2. Структура артефактов

```
docs/
├── WORKFLOW.md                     ← этот документ
├── architecture/
│   ├── overview.md                 ← общая архитектура системы (ведёт architect)
│   ├── conventions.md              ← стандарты кода (ведёт tech-lead, согласует architect)
│   └── adr/
│       └── ADR-NNNN-<slug>.md      ← архитектурные решения
└── features/
    ├── README.md                   ← реестр фич (доска): id, название, статус
    ├── _templates/                 ← шаблоны, НЕ редактировать при работе над фичей
    │   ├── feature.md
    │   ├── architecture.md
    │   └── task.md
    └── F-NNN-<slug>/               ← каталог одной фичи
        ├── feature.md              ← описание фичи (product-manager)
        ├── architecture.md         ← решение по фиче (architect)
        ├── T01-<slug>.md           ← задача 1
        ├── T02-<slug>.md           ← задача 2
        └── ...
version.properties                  ← версия приложения X.Y.Z (ведёт оркестратор, раздел 7)
CHANGELOG.md                        ← журнал «версия → задача → название» (ведёт оркестратор, раздел 7)
```

`version.properties` и `CHANGELOG.md` лежат в корне репозитория. Их меняет только оркестратор при слиянии
задачи в `main` — подраздел «Версия и CHANGELOG при слиянии задачи» в разделе 7.

### Именование
- Фича: `F-NNN-<kebab-slug>`, номер — следующий свободный по `docs/features/README.md`. Пример: `F-001-trip-statistics`.
- Задача: `TNN-<kebab-slug>.md` внутри каталога фичи. Полный id задачи — `F-001/T02`.
- ADR: `ADR-NNNN-<kebab-slug>.md`, сквозная нумерация.
- Slug — на английском, коротко. Содержимое документов — на русском.

### Файл задачи — живой документ
Один файл `TNN-*.md` проходит через всех агентов. Каждый агент **дописывает только свою секцию**
и **добавляет строку в «Журнал»** в конце файла. Чужие секции не переписываются
(исключение: product-manager и architect уточняют описание до статуса `READY`).

## 3. Статусы задачи

```
DRAFT ──architect──► PLAN_REVIEW ──tech-lead──► READY ──developer──► IN_PROGRESS ──► IN_REVIEW
  ▲                       │                                                            │
  └──── NEEDS_REWORK ◄────┘                                                tech-lead   │
                                                                                       ▼
                     DONE ◄──qa── IN_TESTING ◄──────────── approve ─────────── (ревью кода)
                                      │                                                │
                                      └────────► CHANGES_REQUESTED ◄──── reject ───────┘
                                                        │
                                                        └──developer──► IN_PROGRESS ...
Любой статус ──► BLOCKED (с причиной в «Журнале» и вопросом в «Открытые вопросы»)
```

| Статус              | Кто ставит           | Значение                                                         |
|---------------------|----------------------|------------------------------------------------------------------|
| `DRAFT`             | product-manager      | Задача описана с продуктовой стороны                             |
| `PLAN_REVIEW`       | architect            | Добавлен технический план, ждёт ревью тимлида                    |
| `NEEDS_REWORK`      | tech-lead            | План/декомпозиция не принят, замечания в секции «Ревью плана»    |
| `READY`             | tech-lead            | Можно брать в разработку                                         |
| `IN_PROGRESS`       | developer            | В разработке                                                     |
| `IN_REVIEW`         | developer            | Код готов, ждёт код-ревью                                        |
| `CHANGES_REQUESTED` | tech-lead / qa       | Найдены проблемы; замечания в «Ревью кода» или «Тестирование»    |
| `IN_TESTING`        | tech-lead            | Ревью пройдено, ждёт тестирования                                |
| `DONE`              | qa-engineer          | Все критерии приёмки подтверждены                                |
| `BLOCKED`           | любой                | Нужен ответ пользователя или другой задачи                       |

Статус фичи в `feature.md` и `docs/features/README.md`:
`DRAFT → DESIGN → READY → IN_PROGRESS → DONE`. Фича `DONE`, когда все её задачи `DONE`.
Обновляет статус фичи тот агент, чьё действие его изменило.

## 4. Порядок работы над фичей (пайплайн)

1. **Пользователь → product-manager.** PM уточняет цель, создаёт каталог фичи, `feature.md`,
   разбивает фичу на задачи (`T01..TNN`, статус `DRAFT`), регистрирует фичу в `README.md`.
   Неясности → «Открытые вопросы» в `feature.md`; если они блокируют — статус фичи `DRAFT` и вопрос пользователю.
2. **architect.** Читает фичу и `docs/architecture/*`, пишет `architecture.md` фичи, при значимых
   решениях — ADR. В каждую задачу дописывает секцию «Технический план» (затрагиваемые модули,
   контракты, схема БД, зависимости между задачами). Может предложить разбить/объединить задачи —
   правит файлы задач и фиксирует это в журнале. Статус задач → `PLAN_REVIEW`, фичи → `DESIGN`.
3. **tech-lead — ревью плана.** Проверяет декомпозицию, критерии приёмки, реализуемость, соответствие
   `conventions.md`. Итог в «Ревью плана»: `READY` или `NEEDS_REWORK` (→ возврат к architect или PM).
   Когда все задачи `READY` — фича `READY`.
4. **kotlin-backend-developer.** Берёт задачи `READY` в порядке зависимостей (поле `Зависит от`).
   Создаёт ветку задачи (раздел 7), реализует код + unit/integration-тесты, заполняет «Реализация»,
   статус `IN_REVIEW`. Одна задача за запуск, если оркестратор не указал иное.
5. **tech-lead — ревью кода.** Проверяет diff по чек-листу из `conventions.md`. Итог в «Ревью кода»:
   `IN_TESTING` или `CHANGES_REQUESTED` (замечания с пометкой `[blocker]` / `[major]` / `[minor]`).
6. **qa-engineer.** Составляет тест-кейсы по критериям приёмки, дописывает недостающие автотесты
   (в т.ч. негативные и граничные), прогоняет сборку. Итог в «Тестирование»: `DONE` или `CHANGES_REQUESTED`
   с шагами воспроизведения.
7. Цикл 4–6 повторяется до `DONE`. **Лимит: 3 круга** `CHANGES_REQUESTED` на задачу — дальше `BLOCKED`
   и эскалация пользователю.
8. **Задача `DONE` → оркестратор спрашивает пользователя**, сливать ли ветку задачи в `main` (раздел 7).
   При согласии — поднимает версию и пишет строку в `CHANGELOG.md` отдельным коммитом в ветке задачи, затем
   `merge --no-ff` (раздел 7, «Версия и CHANGELOG при слиянии задачи»).

## 5. Общие правила для всех агентов

- **Сначала прочитай**: `docs/WORKFLOW.md`, `docs/features/README.md`, `feature.md` и `architecture.md`
  своей фичи, файл задачи целиком (включая журнал и замечания прошлых кругов).
- **Пиши только в свою секцию** и всегда добавляй строку в «Журнал»:
  `| YYYY-MM-DD | <агент> | <старый статус> → <новый статус> | <кратко что сделано> |`
- **Не выдумывай требования.** Неясно → «Открытые вопросы» + статус `BLOCKED` или вопрос в финальном отчёте.
- **Финальный ответ агента** (который увидит оркестратор) — краткий: какие файлы изменены,
  новые статусы задач, блокеры, что делать следующим шагом.
- Шаблоны в `_templates/` не изменяются без согласования с пользователем.
- `version.properties` и `CHANGELOG.md` меняет **только оркестратор** при слиянии задачи (раздел 7,
  «Версия и CHANGELOG при слиянии задачи»). Агенты их не трогают, если технический план задачи явно этого
  не требует (как в F-012/T01, создавшей эти файлы).

## 6. Оркестрация (для основной сессии Claude Code)

Основная сессия запускает агентов через инструмент Agent, выбирая следующего по статусам:

| Состояние                                 | Кого запускать                          |
|-------------------------------------------|-----------------------------------------|
| Новый запрос фичи от пользователя         | `product-manager`                       |
| Есть задачи `DRAFT` / `NEEDS_REWORK` (план)| `architect`                            |
| Есть задачи `PLAN_REVIEW`                 | `tech-lead` (ревью плана)               |
| Есть задачи `READY` / `CHANGES_REQUESTED` | `kotlin-backend-developer`              |
| Есть задачи `IN_REVIEW`                   | `tech-lead` (ревью кода)                |
| Есть задачи `IN_TESTING`                  | `qa-engineer`                           |
| Есть `BLOCKED` или открытые вопросы       | Спросить пользователя                   |
| Задача стала `DONE`                        | Спросить пользователя о слиянии ветки в `main`; при согласии — поднять версию и слить по разделу 7 |

В промпте агенту всегда указывать путь к фиче/задаче и ветку задачи, например:
`Фича docs/features/F-001-trip-statistics, задача T02, ветка F-001/T02. Выполни свой шаг по docs/WORKFLOW.md.`

Пока одна задача в разработке/ревью/тестировании, оркестратор не запускает параллельно агентов,
которые меняют рабочее дерево в другой ветке (одно рабочее дерево — одна активная ветка).

Команда `/feature <описание>` запускает пайплайн целиком (см. `.claude/commands/feature.md`).

## 7. Работа с git: одна задача — одна ветка

- **Каждая задача** (не фича) делается в **отдельной ветке**, имя которой — полный id задачи:
  `F-NNN/TNN`, например `F-001/T02` (отдельное поле в файле задачи не ведётся — имя ветки равно id задачи).
- **Создаёт ветку** `kotlin-backend-developer` в начале работы над задачей (`READY` → `IN_PROGRESS`):
  от актуального `main`. Если задача из `Зависит от` ещё не слита в `main` — от ветки этой задачи
  (и это фиксируется в «Журнале»). Перед переключением рабочее дерево должно быть чистым;
  если в нём есть чужие незакоммиченные изменения — `BLOCKED` и вопрос оркестратору, ничего не удалять.
- **Вся работа по задаче идёт в её ветке:** код и тесты разработчика, правки после `CHANGES_REQUESTED`,
  автотесты QA, правки документов по задаче (файл задачи, `feature.md`, `README.md`, `conventions.md`, ADR),
  сделанные на этапах разработки, ревью кода и тестирования. Каждый агент перед работой проверяет
  `git branch --show-current` и при необходимости переключается на ветку задачи.
- **Коммиты:** каждый агент, изменивший файлы, в конце своего шага коммитит их в ветку задачи.
  Сообщение: `F-NNN/TNN: <кратко что сделано>` (например, `F-001/T02: каркас Spring Boot и health-check`),
  последней строкой — атрибуция `Co-Authored-By`, если она задана в сессии. Временные файлы и
  артефакты сборки не коммитятся. Хуки не пропускаются (`--no-verify` запрещён).
- **Запрещено** без явного указания пользователя: коммитить в `main`, сливать ветки, `push`,
  `rebase`/`reset --hard`/`push --force`, удалять ветки.
- **Слияние:** когда задача стала `DONE`, оркестратор спрашивает пользователя, сливать ли ветку в `main`.
  При согласии — сначала шаги подраздела «Версия и CHANGELOG при слиянии задачи» (коммит версии в ветке
  задачи), затем `git merge --no-ff F-NNN/TNN` в `main`; ветка после слияния не удаляется без просьбы
  пользователя. Следующая задача ответвляется от обновлённого `main`.
- **Планирование** (PM, architect, ревью плана) идёт до появления веток задач. Документы плана
  оркестратор предлагает закоммитить в `main` при остановке «фича `READY`, начинать ли разработку?».
- **Ревью кода** смотрит изменения ветки относительно базы: `git diff main...F-NNN/TNN`
  (или относительно ветки зависимости, если ответвлялись от неё) и `git log main..F-NNN/TNN`.

### Версия и CHANGELOG при слиянии задачи

Каждая задача, слитая в `main`, получает свою patch-версию SemVer и одну строку в `CHANGELOG.md`
(решение F-012, [ADR-0006](architecture/adr/ADR-0006-app-versioning.md)).

- **Кто:** оркестратор (основная сессия). Агенты `version.properties` и `CHANGELOG.md` не меняют (раздел 5).
- **Когда:** задача `DONE` и пользователь явно согласился слить именно её ветку — сразу перед `merge --no-ff`.
- **Где:** отдельным коммитом **в ветке задачи** `F-NNN/TNN`, поэтому запрет «коммитить в `main`» не нарушается:
  в `main` версия попадает только через `merge --no-ff`. Это единственный коммит оркестратора в ветке задачи
  (кроме вливания `main` в отставшую ветку с согласия пользователя, шаг 4).
- **Когда не поднимается:** задача не `DONE`; пользователь отказался сливать (или ещё не ответил); запись о задаче
  уже есть в `CHANGELOG.md` (повторный запуск процедуры).

**Обозначения и проверки** (все команды — в корне репозитория):
- *Запись задачи* — строка `CHANGELOG.md` полного формата `<X.Y.Z> F-NNN/TNN <название>` с конкретным id задачи.
  Проверяется по всей строке, а не по фрагменту id (строки пояснения в шапке так не начинаются), например:
  `git show main:CHANGELOG.md | grep -E '^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*) F-012/T03 [^[:space:]].*$'`
  (в ветке — то же по файлу `CHANGELOG.md`). Нет файла в `main` — записи в `main` нет.
- *V(main)* — значение `version` из `git show main:version.properties`; *V(ветки)* — из `version.properties` ветки.
- **Ветка актуальна**, если содержит весь текущий `main`: `git merge-base --is-ancestor main F-NNN/TNN`
  (код возврата 0; то же, что `git merge-base main F-NNN/TNN` == `git rev-parse main`). Это **единственный**
  критерий актуальности. Совпадение `V(ветки) == V(main)` — дополнительная проверка, а не критерий: оно лишь
  подтверждает, что задача сама не меняла версию.
- **Особый случай — в `main` ещё нет `version.properties`** (задача, которая вводит версионирование; так было при
  слиянии F-012/T01): сверка `V(ветки) == V(main)` неприменима, актуальность проверяется только по merge-base,
  а базой версии служит значение, созданное в ветке по техническому плану задачи (T01: `1.0.2` → `1.0.3`).

**Процедура:**
1. **Предусловия.** Статус задачи в её файле — `DONE`; пользователь согласился сливать ветку `F-NNN/TNN`;
   `git status` чистый; `git switch F-NNN/TNN`.
2. **Задача уже слита?** Запись задачи есть в `main:CHANGELOG.md` → ничего не делать, сообщить пользователю.
3. **Версия уже поднята?** (повторный запуск после коммита версии.) Запись задачи есть в `CHANGELOG.md` ветки:
   - последний коммит ветки (`git log -1 --format=%s F-NNN/TNN`) — `F-NNN/TNN: версия V`, ветка актуальна
     (merge-base) **и** V(main) равна версии ветки **до** коммита поднятия — значению `version` из
     `git show F-NNN/TNN~1:version.properties` (например, `1.0.3` до поднятия ↔ `1.0.3` в `main`; сверка с версией
     до поднятия, а не «V − 1», верна и для major/minor). Если в `main` нет `version.properties` (особый случай
     выше) — достаточно актуальности по merge-base. Условия выполнены → перейти к шагу 7;
   - иначе (после коммита версии есть другие коммиты, ветка отстала, V(main) не равна версии до поднятия) — стоп
     и вопрос пользователю: `main` изменился после поднятия, номер задублируется или будет конфликт.
4. **Ветка актуальна?** (merge-base, см. выше). Дополнительно, если в `main` есть `version.properties`:
   V(ветки) == V(main); различие при актуальной ветке значит, что задача сама меняла версию, — допустимо, только
   если этого требует её технический план, иначе стоп и вопрос пользователю.
   Ветка **отстала** (ответвилась до слияния другой задачи) → стоп и вопрос пользователю: предложить влить `main`
   в ветку задачи. Это слияние веток — **только с явного согласия пользователя**; `rebase` запрещён. При согласии:
   - в ветке `F-NNN/TNN`: `git merge --no-ff main -m "F-NNN/TNN: влит main перед слиянием" -m "Co-Authored-By: …"`
     (строка `Co-Authored-By` — если задана в сессии; без `--no-verify`); конфликт **в любом файле** — `git merge --abort`, ветку не
     менять, стоп и вопрос пользователю (конфликты самостоятельно не разрешать);
   - при чистом слиянии — `./gradlew clean build` (Windows: `gradlew.bat clean build`) должен быть зелёным;
     красная сборка — стоп и вопрос пользователю (задача может вернуться разработчику);
   - затем процедура **заново с шага 1**.
5. **Поднятие.** База — V(main) (или V(ветки) в особом случае без `version.properties` в `main`):
   `X.Y.Z` → `X.Y.(Z+1)`. В `version.properties` меняется только значение `version`. В `CHANGELOG.md` первой
   записью — над прежней верхней, через пустую строку — добавляется `X.Y.(Z+1) F-NNN/TNN <название>`, где
   название — текст после `# F-NNN/TNN: ` в заголовке файла задачи; остальные строки не меняются
   (`git diff` — одна изменённая строка в `version.properties`, две добавленные в `CHANGELOG.md`: запись и пустая
   строка). Major/minor (`X+1.0.0`, `X.Y+1.0`) — только по явному указанию пользователя, тем же коммитом вместо patch.
6. **Проверка и коммит.** `./gradlew help -q` (Windows: `gradlew.bat help -q`) — версия разбирается без ошибки.
   Коммит **только двух файлов**, независимо от состояния индекса:
   `git commit -m "F-NNN/TNN: версия X.Y.(Z+1)" -m "Co-Authored-By: …" -- version.properties CHANGELOG.md`
   (строка `Co-Authored-By` — если задана в сессии; без `--no-verify`). Затем `git show --stat HEAD` — в коммите
   ровно эти два файла.
7. **Слияние.** `git switch main` → `git merge --no-ff F-NNN/TNN -m "Merge F-NNN/TNN: <название> (X.Y.Z)"`.
   Конфликт или ошибка слияния → `git merge --abort`, `main` не менять (`git status` чистый, `main` указывает на
   прежний коммит), сообщить пользователю; конфликты самостоятельно не разрешать. После успеха: `version.properties`
   в `main` = новой версии, верхняя запись `CHANGELOG.md` — о задаче. Ветка не удаляется. Сообщить пользователю
   новую версию.
8. **Отказ пользователя / задача не `DONE`.** Ни ветка, ни `main` не меняются. При последующем согласии процедура
   выполняется с шага 1 — версия вычисляется на момент слияния.

Последовательные слияния дают последовательные номера без пропусков и повторов: база — всегда текущий `main`
(шаги 3–5), отставшая ветка сначала догоняет `main`, следующая задача ответвляется от обновлённого `main`.
Пример: в `main` `1.0.4`, задача `DONE`, ветка актуальна → коммит `F-NNN/TNN: версия 1.0.5` в ветке → `merge --no-ff`;
повторный запуск находит запись в `main:CHANGELOG.md` и ничего не делает.
