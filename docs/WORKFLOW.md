# Регламент работы команды агентов

Этот документ — **единый источник правды** о процессе. Каждый агент обязан прочитать его
перед началом работы. Если инструкция агента противоречит этому документу — прав этот документ.

---

## 1. Роли

| Агент (subagent)            | Роль                    | Вход                                  | Выход (артефакт)                                        |
|-----------------------------|-------------------------|---------------------------------------|---------------------------------------------------------|
| `product-manager`           | Продукт-менеджер        | Запрос фичи от пользователя           | `feature.md` + файлы задач `T*.md` в статусе `DRAFT`    |
| `architect`                 | Архитектор              | `feature.md`, задачи в `DRAFT`        | `architecture.md`, ADR, задачи в статусе `PLAN_REVIEW`  |
| `tech-lead`                 | Тимлид                  | План (ревью плана) / код (ревью кода) | Секция «Ревью» в задаче, статус `READY` / `IN_TESTING` / `CHANGES_REQUESTED` |
| `kotlin-backend-developer`  | Kotlin backend-разработчик | Задача в `READY` / `CHANGES_REQUESTED` | Код + тесты, секция «Реализация», статус `IN_REVIEW` |
| `qa-engineer`               | Тестировщик             | Задача в `IN_TESTING`                 | Тест-кейсы, автотесты, секция «Тестирование», статус `DONE` / `CHANGES_REQUESTED` |

Субагенты **не вызывают друг друга напрямую**. Оркестратором выступает основная сессия
Claude Code (см. раздел 6) — она запускает агентов по очереди, ориентируясь на статусы в файлах.
Поэтому **всё общение между агентами идёт через файлы**: что не записано в артефакт — того не было.

## 2. Структура артефактов

```
docs/
├── WORKFLOW.md                     ← этот документ
├── architecture/
│   ├── overview.md                 ← общая архитектура системы (ведёт architect)
│   ├── conventions.md              ← стандарты кода (ведёт tech-lead, согласует architect)
│   └── adr/
│       └── ADR-NNNN-<slug>.md      ← архитектурные решения
└── features/
    ├── README.md                   ← реестр фич (доска): id, название, статус
    ├── _templates/                 ← шаблоны, НЕ редактировать при работе над фичей
    │   ├── feature.md
    │   ├── architecture.md
    │   └── task.md
    └── F-NNN-<slug>/               ← каталог одной фичи
        ├── feature.md              ← описание фичи (product-manager)
        ├── architecture.md         ← решение по фиче (architect)
        ├── T01-<slug>.md           ← задача 1
        ├── T02-<slug>.md           ← задача 2
        └── ...
```

### Именование
- Фича: `F-NNN-<kebab-slug>`, номер — следующий свободный по `docs/features/README.md`. Пример: `F-001-trip-statistics`.
- Задача: `TNN-<kebab-slug>.md` внутри каталога фичи. Полный id задачи — `F-001/T02`.
- ADR: `ADR-NNNN-<kebab-slug>.md`, сквозная нумерация.
- Slug — на английском, коротко. Содержимое документов — на русском.

### Файл задачи — живой документ
Один файл `TNN-*.md` проходит через всех агентов. Каждый агент **дописывает только свою секцию**
и **добавляет строку в «Журнал»** в конце файла. Чужие секции не переписываются
(исключение: product-manager и architect уточняют описание до статуса `READY`).

## 3. Статусы задачи

```
DRAFT ──architect──► PLAN_REVIEW ──tech-lead──► READY ──developer──► IN_PROGRESS ──► IN_REVIEW
  ▲                       │                                                            │
  └──── NEEDS_REWORK ◄────┘                                                tech-lead   │
                                                                                       ▼
                     DONE ◄──qa── IN_TESTING ◄──────────── approve ─────────── (ревью кода)
                                      │                                                │
                                      └────────► CHANGES_REQUESTED ◄──── reject ───────┘
                                                        │
                                                        └──developer──► IN_PROGRESS ...
Любой статус ──► BLOCKED (с причиной в «Журнале» и вопросом в «Открытые вопросы»)
```

| Статус              | Кто ставит           | Значение                                                         |
|---------------------|----------------------|------------------------------------------------------------------|
| `DRAFT`             | product-manager      | Задача описана с продуктовой стороны                             |
| `PLAN_REVIEW`       | architect            | Добавлен технический план, ждёт ревью тимлида                    |
| `NEEDS_REWORK`      | tech-lead            | План/декомпозиция не принят, замечания в секции «Ревью плана»    |
| `READY`             | tech-lead            | Можно брать в разработку                                         |
| `IN_PROGRESS`       | developer            | В разработке                                                     |
| `IN_REVIEW`         | developer            | Код готов, ждёт код-ревью                                        |
| `CHANGES_REQUESTED` | tech-lead / qa       | Найдены проблемы; замечания в «Ревью кода» или «Тестирование»    |
| `IN_TESTING`        | tech-lead            | Ревью пройдено, ждёт тестирования                                |
| `DONE`              | qa-engineer          | Все критерии приёмки подтверждены                                |
| `BLOCKED`           | любой                | Нужен ответ пользователя или другой задачи                       |

Статус фичи в `feature.md` и `docs/features/README.md`:
`DRAFT → DESIGN → READY → IN_PROGRESS → DONE`. Фича `DONE`, когда все её задачи `DONE`.
Обновляет статус фичи тот агент, чьё действие его изменило.

## 4. Порядок работы над фичей (пайплайн)

1. **Пользователь → product-manager.** PM уточняет цель, создаёт каталог фичи, `feature.md`,
   разбивает фичу на задачи (`T01..TNN`, статус `DRAFT`), регистрирует фичу в `README.md`.
   Неясности → «Открытые вопросы» в `feature.md`; если они блокируют — статус фичи `DRAFT` и вопрос пользователю.
2. **architect.** Читает фичу и `docs/architecture/*`, пишет `architecture.md` фичи, при значимых
   решениях — ADR. В каждую задачу дописывает секцию «Технический план» (затрагиваемые модули,
   контракты, схема БД, зависимости между задачами). Может предложить разбить/объединить задачи —
   правит файлы задач и фиксирует это в журнале. Статус задач → `PLAN_REVIEW`, фичи → `DESIGN`.
3. **tech-lead — ревью плана.** Проверяет декомпозицию, критерии приёмки, реализуемость, соответствие
   `conventions.md`. Итог в «Ревью плана»: `READY` или `NEEDS_REWORK` (→ возврат к architect или PM).
   Когда все задачи `READY` — фича `READY`.
4. **kotlin-backend-developer.** Берёт задачи `READY` в порядке зависимостей (поле `Зависит от`).
   Реализует код + unit/integration-тесты, заполняет «Реализация», статус `IN_REVIEW`.
   Одна задача за запуск, если оркестратор не указал иное.
5. **tech-lead — ревью кода.** Проверяет diff по чек-листу из `conventions.md`. Итог в «Ревью кода»:
   `IN_TESTING` или `CHANGES_REQUESTED` (замечания с пометкой `[blocker]` / `[major]` / `[minor]`).
6. **qa-engineer.** Составляет тест-кейсы по критериям приёмки, дописывает недостающие автотесты
   (в т.ч. негативные и граничные), прогоняет сборку. Итог в «Тестирование»: `DONE` или `CHANGES_REQUESTED`
   с шагами воспроизведения.
7. Цикл 4–6 повторяется до `DONE`. **Лимит: 3 круга** `CHANGES_REQUESTED` на задачу — дальше `BLOCKED`
   и эскалация пользователю.

## 5. Общие правила для всех агентов

- **Сначала прочитай**: `docs/WORKFLOW.md`, `docs/features/README.md`, `feature.md` и `architecture.md`
  своей фичи, файл задачи целиком (включая журнал и замечания прошлых кругов).
- **Пиши только в свою секцию** и всегда добавляй строку в «Журнал»:
  `| YYYY-MM-DD | <агент> | <старый статус> → <новый статус> | <кратко что сделано> |`
- **Не выдумывай требования.** Неясно → «Открытые вопросы» + статус `BLOCKED` или вопрос в финальном отчёте.
- **Финальный ответ агента** (который увидит оркестратор) — краткий: какие файлы изменены,
  новые статусы задач, блокеры, что делать следующим шагом.
- Шаблоны в `_templates/` не изменяются без согласования с пользователем.

## 6. Оркестрация (для основной сессии Claude Code)

Основная сессия запускает агентов через инструмент Agent, выбирая следующего по статусам:

| Состояние                                 | Кого запускать                          |
|-------------------------------------------|-----------------------------------------|
| Новый запрос фичи от пользователя         | `product-manager`                       |
| Есть задачи `DRAFT` / `NEEDS_REWORK` (план)| `architect`                            |
| Есть задачи `PLAN_REVIEW`                 | `tech-lead` (ревью плана)               |
| Есть задачи `READY` / `CHANGES_REQUESTED` | `kotlin-backend-developer`              |
| Есть задачи `IN_REVIEW`                   | `tech-lead` (ревью кода)                |
| Есть задачи `IN_TESTING`                  | `qa-engineer`                           |
| Есть `BLOCKED` или открытые вопросы       | Спросить пользователя                   |

В промпте агенту всегда указывать путь к фиче/задаче, например:
`Фича docs/features/F-001-trip-statistics, задача T02. Выполни свой шаг по docs/WORKFLOW.md.`

Команда `/feature <описание>` запускает пайплайн целиком (см. `.claude/commands/feature.md`).
