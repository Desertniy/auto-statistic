## Исходный запрос
> Необходимо сделать версионирование приложения. Для этого нужно сделать в корне проект version.properties и CHANGELOG.md. После каждой выполненной задачи должно обновляться эти файлы. В version.properties подниматься версия (начинать будем с 1.0.0), а подниматься будет минорная версия, например, 1.0.1, 1.0.2 и т.д.. В Changelog будет указываться список всех сделанных задач в формате "<номер версии> <номер задачи> <описание задачи>". А так же номер версии должен попадать в сборку приложения, чтобы понимать, какая версия сейчас в проде

Уточнения пользователя (2026-10-24, через оркестратора):
> 1. Поднимается patch-версия по SemVer: 1.0.0 → 1.0.1 → 1.0.2 (пользователь оговорился, назвав её минорной).
> 2. Уже сделанные задачи F-001 (T01–T03) нужно внести в CHANGELOG ретроспективно.
> 3. Версия должна быть видна в имени jar (это минимальное требование «видно в проде»).

Дополнительные ответы пользователя (2026-10-24, через оркестратора):
> - Q2: вариант (а) — версия поднимается и строка в CHANGELOG пишется отдельным коммитом в ветке задачи после согласия пользователя на слияние, сразу перед `merge --no-ff`.
> - Q3a: вариант (б) — своя версия на каждую задачу F-001: T01 = 1.0.0, T02 = 1.0.1, T03 = 1.0.2; стартовое значение version.properties 1.0.2; первая задача F-012 получает 1.0.3.
> - Q4 уточнён: версия должна быть видна в имени jar И в `GET /actuator/info` (без аутентификации). В логе старта — НЕ нужно.

## Проблема и цель
Сейчас у приложения нет осмысленной версии (в сборке — шаблонная `0.0.1-SNAPSHOT`), и нет истории того,
какие задачи в какую версию вошли. По артефакту и по работающему приложению нельзя понять, какой в нём код,
а по репозиторию — что изменилось между версиями.

**Цель:** каждая выполненная задача получает свою patch-версию; есть единый журнал изменений
«версия → задача → описание», включая уже сделанные задачи; версия видна в имени jar и в `GET /actuator/info`.

**Признак успеха:**
- в корне репозитория есть `version.properties` (текущая версия) и `CHANGELOG.md` (все выполненные задачи по версиям,
  начиная с F-001/T01 = `1.0.0`);
- при слиянии каждой выполненной задачи в `main` patch-версия поднимается на 1, в `CHANGELOG.md` появляется строка про задачу;
- имя собранного jar и ответ `GET /actuator/info` содержат версию из `version.properties`; вручную версия нигде не дублируется.

## Пользовательские сценарии
- Как владелец продукта, я хочу по имени jar и по `GET /actuator/info` работающего приложения узнать его версию,
  чтобы знать, какие задачи уже доставлены в прод.
- Как владелец продукта, я хочу открыть `CHANGELOG.md` и увидеть, в какой версии сделана каждая задача
  (включая сделанные до появления версионирования), чтобы отслеживать прогресс и разбирать инциденты по версиям.
- Как оркестратор пайплайна, я хочу иметь чёткое правило, когда и как поднимать версию и писать строку
  в `CHANGELOG.md`, чтобы версия не пропускалась и не поднималась дважды.

## Объём
**Входит:**
- Файл `version.properties` в корне репозитория — единственный источник версии приложения, формат `X.Y.Z`;
  стартовое значение `1.0.2`.
- Файл `CHANGELOG.md` в корне репозитория; одна запись на одну выполненную задачу в формате
  `<номер версии> <номер задачи> <описание задачи>`; ретроспективные записи F-001: `1.0.0 F-001/T01`,
  `1.0.1 F-001/T02`, `1.0.2 F-001/T03`.
- Версия из `version.properties` в имени собранного jar.
- Версия в ответе `GET /actuator/info` без аутентификации; прочие эндпоинты Actuator по HTTP остаются закрытыми;
  в ответе `info` — без путей, хостов, env, секретов.
- Правило процесса в `docs/WORKFLOW.md`: после `DONE` и согласия пользователя на слияние оркестратор отдельным
  коммитом в ветке задачи поднимает patch-версию и дописывает строку в `CHANGELOG.md`, затем `merge --no-ff` в `main`.

**Не входит (out of scope):**
- Вывод версии в лог старта приложения — не нужен (ответ пользователя).
- Автоматическое поднятие версии скриптом/плагином/CI — не запрошено (Допущение: выполняется в рамках процесса).
- Правила поднятия major/minor (`2.0.0`, `1.1.0`) — Допущение: только по явному решению пользователя.
- Git-теги версий, публикация артефактов, релизные заметки для внешних пользователей.
- CI, Docker-образ, деплой (как и в F-001).
- Версионирование API (`/v1/...`) — другое понятие.

## Критерии приёмки фичи
- [ ] AC-1: Given репозиторий после выполнения фичи, When открыть корень проекта, Then в нём есть
  `version.properties` с версией в формате `X.Y.Z` и `CHANGELOG.md`, где каждая запись — строка вида
  `<версия> <F-NNN/TNN> <описание>`.
- [ ] AC-2: Given `CHANGELOG.md`, When прочитать записи, Then в нём есть `1.0.0 F-001/T01 ...`, `1.0.1 F-001/T02 ...`,
  `1.0.2 F-001/T03 ...`, а задачи F-012 идут дальше с `1.0.3` по порядку слияния; версия в `version.properties`
  равна версии самой свежей записи.
- [ ] AC-3: Given в `version.properties` указана версия `1.0.N`, When выполнить `./gradlew build`, Then имя jar
  приложения содержит `1.0.N` (без `SNAPSHOT`); версия не продублирована вручную в других файлах проекта.
- [ ] AC-4: Given приложение собрано с версией `1.0.N` и запущено, When `GET /actuator/info` без аутентификации,
  Then ответ `200` содержит версию `1.0.N`; другие эндпоинты Actuator (кроме `health`) по HTTP недоступны;
  в ответе нет путей, хостов, env, секретов.
- [ ] AC-5: Given версия в `version.properties` изменена, When пересобрать и запустить, Then имя jar и `/actuator/info`
  показывают новую версию; правка других файлов для этого не нужна.
- [ ] AC-6: Given задача F-NNN/TNN `DONE` и пользователь согласился на слияние, When оркестратор выполнил шаг слияния,
  Then в ветке задачи есть отдельный коммит, поднимающий patch-версию ровно на 1 (`1.0.N` → `1.0.N+1`) и добавляющий
  ровно одну строку `1.0.N+1 F-NNN/TNN <описание>` в `CHANGELOG.md`, и после `merge --no-ff` это попало в `main`.
- [ ] AC-7: Given задача не `DONE` или пользователь отказался сливать её ветку, When проверить `version.properties`
  и `CHANGELOG.md` в `main`, Then версия не поднята и записи про эту задачу нет.
- [ ] AC-8: Given правило процесса описано в `docs/WORKFLOW.md`, When оркестратор доводит задачу до слияния, Then из
  регламента однозначно понятно, кто, в какой момент, в какой ветке и каким коммитом обновляет оба файла.
- [ ] AC-9: Given некорректное содержимое `version.properties` (нет файла, нет версии, формат не `X.Y.Z`),
  When выполнить `./gradlew build`, Then сборка падает с понятным сообщением о проблеме с версией (Допущение, Q10).

## Нефункциональные требования
- Версия — один источник правды: `version.properties`. Значение версии не дублируется вручную в коде,
  конфигурации или файлах сборки.
- Безопасность: `/actuator/info` открыт без аутентификации, поэтому отдаёт только версию (и, возможно, имя приложения);
  расширение состава открытых эндпоинтов Actuator — только `info`. Общий харднинг — F-011.
- Сборка по-прежнему работает на Windows и Unix-подобных ОС (как в F-001).
