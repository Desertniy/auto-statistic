## Описание
Требование пользователя «после каждой выполненной задачи должны обновляться `version.properties` и `CHANGELOG.md`»
нужно закрепить в регламенте команды, чтобы версия поднималась всегда, ровно один раз на задачу и в предсказуемый
момент, согласованный с разделом 7 `docs/WORKFLOW.md` (ветка на задачу, слияние в `main` по согласию пользователя).

В `docs/WORKFLOW.md` (и, при необходимости, в инструкциях ответственного агента / оркестратора и команде `/feature`)
описывается:
- **кто** поднимает версию и пишет строку в `CHANGELOG.md` (оркестратор — он выполняет слияние по разделу 7);
- **в какой момент** (решение пользователя по Q2, вариант (а)): после статуса `DONE` и согласия пользователя на слияние —
  **отдельным коммитом в ветке задачи**, сразу перед `merge --no-ff` в `main`;
- **как**: patch-версия по SemVer +1 (`1.0.N` → `1.0.N+1`, подтверждено пользователем, Q1); строка `<новая версия> <F-NNN/TNN> <название задачи>`
  добавляется в `CHANGELOG.md` (новые — вверху, Q6); сообщение коммита — по разделу 7;
- **когда не поднимается**: задача не `DONE`; пользователь отказался сливать ветку; повторный запуск шага для уже
  учтённой задачи (защита от двойного поднятия);
- что делать при изменении первой/второй цифры (только по явному решению пользователя).

Правило применяется начиная с задач самой фичи F-012 (Q5). До слияния T03 оркестратор применяет решение Q2
напрямую (F-012/T01 при слиянии получает `1.0.3`); после слияния T03 правило действует по регламенту.
Сама T03 тоже получает свою версию при слиянии.

## Критерии приёмки
- [ ] AC-1: Given обновлённый `docs/WORKFLOW.md`, When прочитать раздел о версионировании, Then однозначно указано:
  кто обновляет файлы, на каком шаге пайплайна, в какой ветке, каким коммитом (формат сообщения), как вычисляется
  новая версия и как выглядит строка `CHANGELOG.md`.
- [ ] AC-2: Given таблица оркестрации (раздел 6) и раздел 7 `WORKFLOW.md`, When сверить их с новым правилом, Then
  противоречий нет: шаг «задача `DONE` → спросить пользователя о слиянии» при согласии включает отдельный коммит
  «версия + строка CHANGELOG» в ветке задачи и затем `merge --no-ff`; запрет коммитов в `main` не нарушается.
- [ ] AC-3: Given текущая версия `1.0.N` и задача F-NNN/TNN доведена до момента поднятия версии, When выполнить
  шаг по правилу, Then в `main` после слияния `version.properties` = `1.0.N+1`, в `CHANGELOG.md` ровно одна новая
  строка `1.0.N+1 F-NNN/TNN <название задачи>`; другие строки не изменены.
- [ ] AC-4 (негативный): Given пользователь отказался сливать ветку задачи (или задача не `DONE`), When проверить
  `main`, Then версия и `CHANGELOG.md` в `main` не изменились.
- [ ] AC-5 (граничный): Given для задачи F-NNN/TNN строка в `CHANGELOG.md` уже есть, When шаг выполняется повторно,
  Then версия второй раз не поднимается и дубликат строки не появляется — правило явно требует проверить это.
- [ ] AC-6 (граничный): Given две задачи сливаются в `main` последовательно, When обе прошли шаг, Then у них
  разные последовательные версии (`1.0.N+1`, `1.0.N+2`), без пропусков и повторов номеров.
- [ ] AC-7: Given инструкции агентов (`.claude/agents/`) и команда `.claude/commands/feature.md`, When прочитать
  инструкции того, кто по правилу обновляет версию, Then в них есть ссылка на правило / шаг про версию; инструкции
  других агентов не требуют от них поднимать версию. Шаблоны `docs/features/_templates/` не меняются без согласия
  пользователя (Q9 фичи).
- [ ] AC-8: Given изменения задачи, When выполнить `./gradlew build`, Then сборка зелёная (задача документационная,
  код не затрагивается).

## Открытые вопросы
- Q2 закрыт пользователем (вариант (а)).
- Q5 (все задачи поднимают версию), Q6 (описание = название задачи, новые строки вверху), Q7 (одна задача — одна
  версия), Q9 (правка `.claude/agents/`, `.claude/commands/` и шаблонов) — приняты допущения.

## Технический план
- **Предусловие:** F-012/T01 слита в `main` (в `main` есть `version.properties` = `1.0.3` и `CHANGELOG.md`); ветка
  `F-012/T03` — от `main`. Задача документационная: код и сборка не меняются.
- **Модули / пакеты (файлы):** содержание правила — [architecture.md](./architecture.md), «Поток 3» (это спецификация;
  перенести в регламент по смыслу полностью, формулировки — на усмотрение разработчика).
  - `docs/WORKFLOW.md`:
    - **Раздел 7** — новый подраздел в конце, `### Версия и CHANGELOG при слиянии задачи`: исполнитель (оркестратор),
      предусловия, защита от двойного поднятия (проверка записи `F-NNN/TNN` в `main:CHANGELOG.md` и в ветке),
      защита от устаревшей ветки (`version.properties` ветки == `main`, иначе стоп и вопрос пользователю), вычисление
      `X.Y.Z` → `X.Y.(Z+1)`, формат и место строки CHANGELOG (первая запись, пустая строка между записями, название —
      из заголовка файла задачи), проверка `gradlew help -q`, коммит только двух файлов с сообщением
      `F-NNN/TNN: версия X.Y.Z` (+ `Co-Authored-By`, без `--no-verify`), затем `git switch main` и `git merge --no-ff`;
      отказ пользователя / задача не `DONE` → ничего не меняется; major/minor — только по явному указанию пользователя.
      Явно: коммит версии делается **в ветке задачи**, поэтому запрет «коммитить в `main`» не нарушается; это
      единственный коммит оркестратора в ветке задачи.
    - **Раздел 7, пункт «Слияние»** — дополнить: «перед `merge --no-ff` — шаги подраздела „Версия и CHANGELOG…“».
    - **Раздел 6**, строка таблицы «Задача стала `DONE`» — «Спросить пользователя о слиянии; при согласии — поднять
      версию и слить по разделу 7».
    - **Раздел 4**, шаг 8 — то же одной фразой со ссылкой на раздел 7.
    - **Раздел 5** — общее правило: `version.properties` и `CHANGELOG.md` меняет только оркестратор по разделу 7;
      агенты их не трогают, если технический план задачи явно не требует (как F-012/T01).
    - **Раздел 2** — в дереве артефактов/под ним упомянуть корневые `version.properties` и `CHANGELOG.md` (кто ведёт — оркестратор).
  - `.claude/commands/feature.md`, п. 3 (пункт про `DONE`): при согласии пользователя — поднять версию и записать
    CHANGELOG по разделу 7 `docs/WORKFLOW.md`, затем `merge --no-ff`; в п. 5 (сводка) — указать новую версию.
  - `.claude/agents/kotlin-backend-developer.md` и `.claude/agents/qa-engineer.md` — по одной строке: не менять
    `version.properties`/`CHANGELOG.md` (их меняет оркестратор при слиянии, `WORKFLOW.md` раздел 7), кроме случаев, когда
    этого явно требует технический план.
  - `.claude/agents/tech-lead.md`, режим ревью кода — строка: правка `version.properties`/`CHANGELOG.md` в ветке задачи
    без основания в плане — `[major]`.
  - **Не менять:** `docs/features/_templates/*` (Q9 — без согласия пользователя), `CLAUDE.md` (отсылает к `WORKFLOW.md`),

    и `CHANGELOG.md` (их в этой ветке изменит только оркестратор при слиянии T03 → `1.0.4`).
- **API-контракт / модель данных / доменные типы:** нет.
- **Ключевые решения:** [ADR-0006](../../architecture/adr/ADR-0006-app-versioning.md) п. 6; architecture.md «Поток 3».
  Защита от двойного поднятия — по наличию записи `F-NNN/TNN` в CHANGELOG (`main` и ветки), а не по памяти оркестратора;

- **Проверка (QA):** AC-1, AC-2, AC-7 — чтение `WORKFLOW.md` §2, §4–§7, `feature.md` команды и агентов: нет

  отказ; повторный запуск после коммита версии) + фактическая история `main` после слияния T01 (`1.0.3`, отдельный

  `gradlew help`. Отставшая ветка задачи → конфликт в двух файлах → правило требует остановиться и спросить пользователя.

## Ревью плана
- Вердикт: **READY** (п. 1–3 — обязательные дополнения текста правила при переносе «Потока 3» в `WORKFLOW.md`;
  оркестратор применяет их уже при слиянии F-012/T01)
- Сверка с разделом 7 `WORKFLOW.md`: противоречий нет — коммит версии делается в ветке задачи (запрет коммитов в
  `main` не нарушается), слияние — только по согласию пользователя, `merge --no-ff`, ветка не удаляется, `rebase`
  не используется. Защита от двойного поднятия по записи в `CHANGELOG.md` (`main` и ветки), база версии — `main`:
  последовательные номера (AC-6) обеспечены. Состав правок (§2, §4 п. 8, §5, §6, §7; `feature.md` команды;
  developer/qa/tech-lead) полный; шаблоны и `CLAUDE.md` не трогаются (Q9) — верно.
- Замечания:
  1. **[обязательно] Ветка «поднятие уже сделано» пропускает проверку базы.** В «Потоке 3», шаг 2 (и на схеме
     `D -- да, и это последний коммит ветки --> M`) при уже сделанном коммите версии сразу идёт слияние без шага 3.
     Если между коммитом версии и слиянием `main` изменился, номер задублируется или будет конфликт. → В правиле:
     «запись есть и последний коммит — `F-NNN/TNN: версия V`» → дополнительно проверить, что `main:version.properties`
     = V−1 (patch); иначе стоп и вопрос пользователю.
  2. **[обязательно] Конфликт/ошибка при `merge --no-ff` (шаг 6).** Не описано. → `git merge --abort`, `main` не
     менять, сообщить пользователю; конфликты самостоятельно не разрешать (как в шаге 3).
  3. **[обязательно] Отставшая ветка (шаг 3).** «Предложить влить `main` в ветку задачи» — это слияние веток,
     только по явному согласию пользователя (раздел 7, «Запрещено»). Дописать, что после такого слияния: конфликты
     вне `version.properties`/`CHANGELOG.md` — стоп и вопрос; при чистом слиянии — `./gradlew build` зелёный, затем
     процедура заново с шага 1. Без этого отставшая ветка уходит в `main` с непроверенным кодом.
  4. [minor] Шаг 5: «коммит только двух файлов» надёжнее закрепить командой, не зависящей от состояния индекса:
     `git commit -- version.properties CHANGELOG.md` (или проверка `git diff --cached --name-only` перед коммитом);
     предусловие «`git status` чистый» оставить.
  5. [minor] Шаг 2: проверку записи формулировать как совпадение строки по regex записи из architecture.md
     («Модель данных») с конкретным `F-NNN/TNN`, а не произвольной `^\S+ F-NNN/TNN `, чтобы строки пояснения не давали
     ложных срабатываний (сейчас их нет, но формат пояснения может меняться).
  6. [minor] QA: AC-3/AC-6 подтверждаются фактической историей `main` (слияния T01 → `1.0.3`, T03 → `1.0.4`) — это
     происходит после `DONE` T03; в «Тестировании» явно разделить «проверено чтением/table-top» и «подтверждено
     историей слияния T01», чтобы `DONE` не зависел от будущего действия оркестратора.

  `version.properties`, `CHANGELOG.md`.
- **Что сделано:** «Поток 3» из architecture.md перенесён в `WORKFLOW.md` §7 как процедура из 8 шагов: кто
  (оркестратор), когда (`DONE` + согласие), где (отдельный коммит в ветке задачи — запрет коммитов в `main` не
  нарушается), как (patch+1, первая запись CHANGELOG через пустую строку, название из заголовка задачи,
  `gradlew help -q`, сообщение `F-NNN/TNN: версия X.Y.Z`), когда не поднимается, major/minor — только по указанию
  пользователя. Обязательные дополнения ревью плана:
  1. повторный запуск после коммита версии (шаг 3) — к слиянию только если последний коммит `F-NNN/TNN: версия V`,
     ветка актуальна и V(main) = V − 1, иначе стоп и вопрос;
  2. конфликт/ошибка `merge --no-ff` (шаг 7) — `git merge --abort`, `main` не менять, сообщить пользователю;
  3. отставшая ветка (шаг 4) — вливание `main` в ветку только с согласия пользователя; конфликт → `merge --abort`
     и вопрос; чистое слияние → `./gradlew clean build` зелёный → процедура с шага 1.
  Minor: коммит `git commit … -- version.properties CHANGELOG.md` + `git show --stat HEAD`; запись задачи
  проверяется по полному формату строки (`grep -E` с regex из architecture.md и конкретным id).
  По опыту слияния T01: критерий актуальности ветки — только `git merge-base --is-ancestor main F-NNN/TNN`;
  `V(ветки) == V(main)` — дополнительная проверка; описан особый случай «в `main` нет `version.properties`»
  (сверка неприменима, база — значение из ветки по плану задачи, как T01: `1.0.2` → `1.0.3`).
  Команды проверки записи и merge-base опробованы на текущем `main` (запись F-012/T01 находится, F-012/T03 — нет).
- **Тесты:** код не менялся, автотестов нет (задача документационная). `./gradlew clean build` — BUILD SUCCESSFUL,
  10 тестов в 5 спецификациях, 0 падений; jar `build/libs/auto-statistic-1.0.3.jar`.
- **Отклонения от плана:** (1) при отставшей ветке любой конфликт при вливании `main` (в т. ч. в
  `version.properties`/`CHANGELOG.md`) ведёт к `merge --abort` и вопросу — строже ревью, т.к. ветка эти файлы
  менять не должна; (2) в шаге 3 для случая без `version.properties` в `main` сверка V − 1 идёт с
  `F-NNN/TNN~1:version.properties`; (3) mermaid-схема в `WORKFLOW.md` не перенесена — шаги исчерпывающие, схема
  остаётся в architecture.md (её ветка «сразу merge» уточнена текстом шага 3); (4) в `feature.md` команды п. 5
  дополнен текущей версией в сводке; в qa-engineer оговорены временные правки для негативных проверок.
